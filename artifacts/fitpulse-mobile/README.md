# GYM Buddy mobile

The mobile app uses five bottom destinations: Today, Log (Nutrition and Strength), Movement, Insights, and Plan. It keeps the GYM Buddy website's colors and style without changing the website's visual layout. An unpaired phone keeps its fitness journal locally. Once paired with the website's Movement key, meals, saved meal templates, strength sets and completed workouts, completed live sessions, water and weight records, and supported goals sync through the shared API. The original local records remain in place. Conflicting edits are preserved and reported rather than silently replacing one another; there is not yet an interactive conflict-resolution screen. Active workout drafts and fasting timers stay on the device. Paired native/manual Movement data retains its separate sync path.

On iOS, Expo Pedometer uses Core Motion. With Motion & Fitness permission and a supported physical device, `getStepCountAsync` reads historical step totals over a requested interval, limited to the past seven days. The app queries local hourly intervals on launch and when it returns to the foreground, then replaces each day's native snapshot on the paired GYM Buddy account. No JavaScript listener is claimed to keep running while locked.

Expo Pedometer's `watchStepCount` does **not** deliver updates in the background. Its historical `getStepCountAsync` is **iOS only**. Android in this Expo Go-compatible version therefore does not promise locked-screen history; it can still display and add paired manual steps. An Android implementation would need a separate supported Health Connect integration and user consent.

Sources: [Expo Pedometer](https://docs.expo.dev/versions/latest/sdk/pedometer/), [Apple CMPedometer historical queries](https://developer.apple.com/documentation/coremotion/cmpedometer/querypedometerdata(from:to:withhandler:)).

The movement tables are defined in the shared Drizzle schema. The configured post-merge setup pushes this schema to the development database. Replit Publish applies the development-to-production schema diff when the project is published; the API intentionally does not modify schema on startup.

Pairing: create the private key in the web Movement view, paste it into the mobile app. The key is a bearer credential; the server stores its hash, while the phone stores the key in SecureStore. Keep it private. Existing browser sensor estimates and old manual entries cannot be distinguished. When a native snapshot arrives for that date it replaces that older browser total, not adds to it. New manual additions use separate idempotent event IDs, so refreshes of native history do not double-count them. Clearing manual steps never erases native phone history.

In the browser preview only, pairing uses browser-local storage because SecureStore is not available there. Browser previews cannot read the native step sensor.

The iOS home-screen widget displays dated daily progress and opens GYM Buddy for quick logging. It needs an iOS development build: Expo Go and the web preview cannot render it. The widget publishes a timeline entry at the next local midnight to avoid labeling yesterday's numbers as today's. Android home-screen widgets are not supported by the current iOS-only Expo Widgets module.
